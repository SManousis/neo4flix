# 9. Login, security, and two-factor authentication

Security is easier to understand when two ideas are separated:

- **Authentication** answers “who is making this request?”
- **Authorization** answers “is that identity allowed to do this?”

Neo4flix authenticates users with passwords, access tokens, refresh tokens,
and optional TOTP two-factor authentication. It authorizes operations using the
`USER` and `ADMIN` roles plus resource ownership rules.

## Registration and password storage

During registration, User Service validates the input and passes the password
through BCrypt. BCrypt is a deliberately slow password-hashing algorithm. The
database stores the hash, not the original password.

The password policy requires:

- at least 10 characters;
- at least one uppercase letter;
- at least one lowercase letter;
- at least one digit;
- at least one non-alphanumeric character; and
- no whitespace or control characters.

The exact policy is implemented in
[`PasswordPolicy`](../../backend/user-service/src/main/java/com/neo4flix/user/auth/PasswordPolicy.java).

A password hash cannot be “decrypted” to reveal the original password. At
login, BCrypt checks whether the submitted password produces a matching result.

## The normal login flow

```text
Browser                         User Service
   |                                 |
   | POST /auth/login                |
   | email + password                |
   |-------------------------------->|
   |                                 | verify account and BCrypt hash
   |                                 | create access + refresh tokens
   | access token in JSON            |
   | refresh token in secure cookie  |
   |<--------------------------------|
```

The browser uses the two tokens differently.

## Access tokens and JWT

An access token is a short-lived **JWT**—JSON Web Token. It contains signed
claims such as:

- `sub`: the user ID;
- `roles`: the user's role;
- `iss`: the expected issuer;
- `aud`: the intended audience;
- `iat`: issue time;
- `exp`: expiry time; and
- `jti`: a unique token ID.

User Service signs the token using the RS256 algorithm and the private RSA key.
Other services validate that signature with the corresponding public key. They
also check issuer, audience, and expiration before trusting the identity.

[`JwtTokenService`](../../backend/user-service/src/main/java/com/neo4flix/user/security/JwtTokenService.java)
issues tokens. Shared validation is configured in
[`ResourceServerSecurityConfig`](../../backend/platform-common/src/main/java/com/neo4flix/platform/common/security/ResourceServerSecurityConfig.java).

Angular keeps the access token in memory. The authentication interceptor sends
it in an HTTP header:

```http
Authorization: Bearer eyJ...
```

## Refresh tokens

Access tokens expire quickly to limit the lifetime of a stolen token. A refresh
token lets the browser request a new access token without asking for the
password every few minutes.

Neo4flix places the refresh token in a cookie with restrictive attributes,
including HTTP-only and SameSite settings. HTTP-only means frontend JavaScript
cannot read the token.

The server stores only a SHA-256 hash of the refresh token. Refreshing rotates
the token: the old session is revoked and a replacement is issued. Logout
revokes the current refresh session and clears the cookie.

## What 2FA adds

Two-factor authentication requires something the user knows—the password—and
something the user has—the changing code generated by an authenticator app.

Neo4flix uses **TOTP**, Time-based One-Time Passwords. The current time and a
shared secret produce a six-digit code that changes every 30 seconds.

### Enrollment

```text
Authenticated user
  -> request 2FA setup
  -> server creates a pending secret
  -> user scans/enters it in an authenticator app
  -> user submits the current six-digit code
  -> server verifies it
  -> pending setup becomes active 2FA
```

The setup does not become active until confirmation succeeds. The TOTP secret
is encrypted before persistence.

### Login with 2FA

```text
correct email/password
  -> temporary 2FA challenge, not a normal login
  -> user submits challenge token + TOTP code
  -> server verifies expiry, ownership, code, and replay rules
  -> normal access/refresh tokens are issued
```

The low-level code generation and checking is in
[`TotpService`](../../backend/user-service/src/main/java/com/neo4flix/user/security/TotpService.java),
while
[`TotpAuthenticationService`](../../backend/user-service/src/main/java/com/neo4flix/user/auth/TotpAuthenticationService.java)
coordinates enrollment and challenges.

## Authorization and roles

Neo4flix has two roles:

- `USER`: normal account actions; and
- `ADMIN`: normal actions plus catalog administration.

The backend security configuration decides which API paths are public,
authenticated, or admin-only. Controllers also use the JWT subject to ensure a
user acts on their own profile, ratings, watchlist, and shares.

Angular guards improve the experience by preventing navigation to inappropriate
pages, but browser code can be modified by a user. Backend checks are therefore
authoritative.

## Other protections

The project also includes:

- input validation and bounded query parameters;
- parameterized Cypher queries;
- CORS restrictions for approved frontend origins;
- rate limiting for login and expensive Nginx routes;
- security response headers from Nginx;
- consistent generic authentication errors;
- request IDs for safe troubleshooting;
- encrypted TOTP secrets; and
- rules preventing secrets from appearing in public response DTOs.

## Local HTTPS limitation

The local Compose profile serves HTTP. Production HTTPS termination,
certificate handling, HTTPS redirects, and HSTS require deployment evidence and
are not proven by the local stack. This distinction is recorded in the
[`SECURITY_CHECKLIST`](../audit/SECURITY_CHECKLIST.md).

## Recap

Passwords are hashed, User Service signs short-lived JWT access tokens, refresh
tokens rotate through HTTP-only cookies, all protected services validate the
same token contract, and optional TOTP adds a second login factor. Backend
authorization—not Angular guards—protects data and operations.
